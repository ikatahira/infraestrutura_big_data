📚 Recapitulando a Semana 02 — antes de continuar
Na semana passada você aprendeu que toda infraestrutura de Big Data depende de máquinas se encontrando na rede: IP (o endereço), porta (o apartamento/serviço) e protocolo TCP/IP (o idioma combinado para trocar dados sem perder nada no caminho). Viu também que praticamente toda ferramenta de Big Data segue o padrão cliente-servidor e, dentro dele, o padrão master/worker — um nó coordenando vários outros, como no MapReduce. E praticou tudo isso no terminal Ubuntu com ip a, ping, ss, nslookup/dig e curl.

Hoje a pergunta muda de "como as máquinas conversam entre si?" para "de onde vêm essas máquinas, afinal?" — e a resposta é a virtualização que você já usa desde a Semana 01 (sua VM Ubuntu dentro do VirtualBox), sem ainda saber o nome técnico de cada peça. É exatamente isso que vamos formalizar agora, e depois ver como esse mesmo princípio escala para clusters inteiros alugados na nuvem.

🧩 Virtualização — Um Computador Dentro do Outro
Na Semana 01, você criou uma VM Ubuntu dentro do VirtualBox sem parar muito para pensar no que estava acontecendo por baixo. Vamos formalizar isso.

Hypervisor — o software que cria e gerencia máquinas virtuais (o VirtualBox é um hypervisor tipo 2, que roda sobre um SO já instalado; existem também hypervisors tipo 1, que rodam direto no hardware, comuns em servidores de datacenter).

Virtualização de hardware — o hypervisor "finge" para o sistema convidado (guest) que ele tem CPU, RAM e disco dedicados só para ele — mesmo compartilhando o hardware físico (host) com outras VMs.

VT-x / AMD-V — lembra da Semana 01? Esse é o recurso do processador físico que permite a virtualização acontecer com boa performance, em vez de simular tudo por software (o que seria extremamente lento).

Por que isso importa para clusters — um datacenter real não tem uma máquina física para cada nó do cluster. Ele roda dezenas de VMs por servidor físico, multiplicando a capacidade sem multiplicar o hardware.

Agora que você entende virtualização localmente, vamos ver como isso se transforma em um serviço que você aluga por hora.
☁️ Cloud Computing — Alugar em vez de Comprar Hardware
Conecta direto com a ementa ("recursos de hardware para Big Data"): hoje, a maioria das empresas não compra e mantém servidores próprios — aluga capacidade computacional sob demanda.

IaaS (Infrastructure as a Service) — você aluga só a máquina virtual crua (CPU, RAM, disco, rede) e instala tudo você mesmo, como estamos fazendo com Hadoop/Spark. Ex: AWS EC2, Google Compute Engine.

PaaS (Platform as a Service) — o provedor já entrega a ferramenta pronta para uso, sem você precisar instalar nada. Ex: AWS EMR (Hadoop/Spark já configurado), Google Dataproc.

SaaS (Software as a Service) — a aplicação final já pronta para o usuário final usar direto no navegador. Ex: Google Analytics, Gmail.

Elasticidade — a maior vantagem da nuvem: um cluster pode crescer de 3 para 300 máquinas em minutos quando o volume de dados aumenta, e encolher de novo depois — pagando só pelo que usa, ao contrário de comprar hardware que fica ocioso na maior parte do tempo.

Contêineres (Docker) — uma forma mais leve de empacotar aplicações: em vez de uma VM inteira, empacota só a aplicação e suas dependências. Sobe muito mais rápido que uma VM completa — cada vez mais usado para subir ambientes de Big Data de teste rapidamente.

🛠️ Prática — Explorando Redes de VM e um Provedor de Nuvem Gratuito
⚡ +200 XP ⏱ ~25 min Prática 📋 Ementa: Modos de configuração e funcionamento de um sistema para Big Data
⚡

Vamos conectar teoria com prática: primeiro revisitando as configurações da sua própria VM, depois dando uma espiada em como a nuvem real se parece.
01
Explorar as configurações de rede da sua VM no VirtualBox
Abra as configurações da sua VM Ubuntu (com a VM desligada) → aba Rede, e observe as opções:
ℹ️ NAT (padrão): sua VM acessa a internet através do seu computador, mas fica "escondida" da rede local — mais simples, menos exposta.
Bridge: sua VM aparece na rede local como se fosse uma máquina física própria, com seu próprio IP visível para outros dispositivos — necessário se você quiser que outra VM se conecte diretamente na sua (útil para simular um cluster com mais de 1 nó).
02
Tirar um Snapshot da sua VM
Snapshots são um recurso de virtualização puro — salvam o estado exato da VM para poder voltar depois:
bash
# No VirtualBox: Máquina > Tirar Instantâneo # Isso salva RAM + disco no exato momento atual
⚠️ Prática recomendada: tire um snapshot da sua VM agora, com Hadoop instalado e funcionando (Semana 05 em diante) — se algo quebrar numa instalação futura, você volta pra esse ponto em segundos.
03
Criar uma conta gratuita em um provedor de nuvem
Escolha um: AWS Free Tier, Google Cloud Free Tier, ou Azure for Students. Todos oferecem crédito/uso gratuito para testes.
text
AWS Free Tier: aws.amazon.com/free Google Cloud Free Tier: cloud.google.com/free Azure for Students: azure.microsoft.com/free/students
04
Explorar o console (sem precisar criar nada pago)
Entre no console do provedor escolhido e localize onde você criaria uma máquina virtual (EC2 na AWS, Compute Engine no Google) — apenas observe as opções de CPU/RAM disponíveis, sem criar de fato.
