Por que Spark? O contexto da evolução dos frameworks

O MapReduce foi revolucionário em 2004, mas tem uma limitação importante: ele grava os resultados intermediários em disco entre cada fase Map e Reduce. O Spark (2009, UC Berkeley) surgiu para resolver isso mantendo os dados em memória RAM (RDD — Resilient Distributed Dataset), podendo ser 10 a 100× mais rápido em operações iterativas.

💡 Foco do artigo: O grupo não precisa configurar Spark no HDFS — basta usar o modo local[*] do Spark sobre arquivos locais e comparar com o job MapReduce no HDFS. O que importa é a análise conceitual e os números de tempo.

#!/usr/bin/env python3 import sys, time from pyspark import SparkContext, SparkConf conf = SparkConf().setAppName("WordCount").setMaster("local[*]") sc = SparkContext(conf=conf) sc.setLogLevel("WARN") start = time.time() text = sc.textFile(sys.argv[1]) counts = (text.flatMap(lambda line: line.lower().split()) .map(lambda word: (word, 1)) .reduceByKey(lambda a, b: a + b) .sortBy(lambda x: x[1], ascending=False)) result = counts.take(10) elapsed = time.time() - start print(f"\n[SPARK] Top 10 palavras:") for word, count in result: print(f" {word}: {count}") print(f"[SPARK] Tempo total: {elapsed:.4f}s") sc.stop() # Execução: $ time python3 wordcount_spark.py corpus_10mb.txt

1

Fundamentos de tolerância a falhas no HDFS — o que estudar

O HDFS foi projetado com a premissa de que falhas de hardware são a norma, não a exceção. Seus mecanismos de resiliência incluem:

REPLICAÇÃO

Fator de réplica 3

Cada bloco de 128 MB é replicado em 3 DataNodes distintos. Se um falhar, os dados permanecem acessíveis

HEARTBEAT

Sinal de vida dos DataNodes

A cada 3 segundos, cada DataNode envia um heartbeat ao NameNode. Após 10 heartbeats perdidos, é declarado morto

BLOCK REPORT

Inventário de blocos

Periodicamente, DataNodes informam ao NameNode quais blocos possuem — permite detectar corrupção ou falta

REREPLICA

Re-replicação automática

Quando um DataNode morre, o NameNode detecta blocos sub-replicados e ordena re-replicação nos nós vivos

📌 Limitação do modo pseudo-distribuído: Com apenas 1 DataNode, não é possível simular a re-replicação automática (não há outro nó para replicar). O artigo deve descrever o que ocorreria em cluster real — isso é análise teórica válida e esperada.
2

Experimentos práticos de simulação de falhas

  Experimento 1 — Matar o DataNode e observar o NameNode
# 1. Certifique-se de que o cluster está rodando e tem dados no HDFS $ jps NameNode, DataNode, SecondaryNameNode, ResourceManager, NodeManager # 2. Carregue um arquivo de teste se ainda não tiver $ hdfs dfs -put corpus.txt /user/hadoop/input/ $ hdfs fsck /user/hadoop/input/corpus.txt -files -blocks # Anote o estado HEALTHY antes da falha # 3. Mate SOMENTE o processo DataNode (sem parar o NameNode) $ kill -9 $(jps | grep DataNode | awk '{print $1}') $ jps # DataNode deve ter sumido da lista # 4. Tente acessar o arquivo — pode demorar até o timeout do heartbeat $ hdfs dfs -ls /user/hadoop/input/ $ hdfs fsck /user/hadoop/input/corpus.txt # Observe mensagens de MISSING blocks ou UNDER REPLICATED # 5. Monitore o log do NameNode para ver detecção de falha $ tail -f $HADOOP_HOME/logs/hadoop-hadoop-namenode-*.log | grep -i "dead\|lost\|unreachable"
  Experimento 2 — Reiniciar o DataNode e verificar recuperação
# Reinicie apenas o DataNode $ hdfs --daemon start datanode $ jps # DataNode deve reaparecer # Verifique a integridade dos dados após a recuperação $ hdfs fsck /user/hadoop/input/corpus.txt -files -blocks # Status deve voltar a HEALTHY # Verifique no log o re-registro do DataNode $ tail -20 $HADOOP_HOME/logs/hadoop-hadoop-namenode-*.log # Experimento 3 — Corrupção teórica: verificar checksums $ hdfs fsck / -includeSnapshots -blocks # Procure por "CORRUPT BLOCKS" — em ambiente limpo deve ser 0
⚠ Atenção: Após matar o DataNode, aguarde pelo menos 30 segundos antes de tentar acessar os dados. O NameNode precisa passar pelo timeout de detecção de falha para declarar o nó como morto. O comportamento exato depende da configuração de dfs.heartbeat.interval.

Análise teórica: o que aconteceria em cluster real de 3 nós

📄 CENÁRIO TEÓRICO — DESCREVER NO ARTIGO

Com 3 DataNodes (replication factor = 3), cada bloco existe em 3 cópias em nós diferentes. Quando o DataNode 2 falha:

1. Após ~30s sem heartbeat, NameNode declara DataNode 2 como morto.
2. NameNode verifica quais blocos estavam no DataNode 2 (via último block report).
3. Para cada bloco agora com apenas 2 réplicas, NameNode seleciona um DataNode vivo e ordena re-replicação.
4. DataNode 1 ou 3 copia o bloco deficiente para outro nó disponível.
5. Quando DataNode 2 se recupera, NameNode pode opcionalmente remover réplicas em excesso.

Em pseudo-distribuído (1 DataNode), a etapa 3-4 não acontece — não há onde replicar.
