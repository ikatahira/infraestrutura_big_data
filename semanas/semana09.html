Arquitetura do Kafka

🤔 Por que precisamos de streaming?

Imagine que um sistema de e-commerce registra um pedido. O banco de dados precisa ser atualizado, o time de estoque precisa ser notificado, o sistema de pagamento precisa ser acionado e um e-mail de confirmação precisa ser enviado — tudo de forma coordenada. A solução tradicional seria conectar esses sistemas diretamente, criando um emaranhado de integrações ponto-a-ponto que se torna impossível de manter. O Kafka resolve isso com um barramento de eventos centralizado: cada sistema publica eventos em tópicos, e qualquer sistema interessado consome esses eventos de forma independente. O resultado é uma arquitetura desacoplada, resiliente e escalável.

🖥
Broker
Um servidor Kafka. Em produção, múltiplos brokers formam um cluster para replicação e alta disponibilidade. Cada broker armazena partições dos tópicos.
📂
Topic
Canal lógico onde mensagens são publicadas. Similar a uma tabela ou fila, mas persistente e imutável — mensagens publicadas não são deletadas ao ser consumidas.
🔀
Partition
Cada topic é dividido em N partições. Cada partição é uma sequência ordenada e imutável de mensagens. Mais partições = mais paralelismo de leitura/escrita.
📍
Offset
Número sequencial que identifica unicamente cada mensagem dentro de uma partição. Consumers controlam seu próprio offset — podem reler mensagens antigas.
📤
Producer
Aplicação que publica mensagens em um tópico. O producer escolhe em qual partição escrever (por key hash ou round-robin). Pode configurar garantias de entrega.
📥
Consumer
Aplicação que lê mensagens de um tópico. Cada consumer lembra seu offset — se cair e reiniciar, retoma de onde parou. Pode reler mensagens antigas.
👥
Consumer Group
Grupo de consumers que dividem o trabalho: cada partição é atribuída a um consumer do grupo. Com 4 partições e 2 consumers, cada um lê 2 partições. Escala horizontal!
🏛
KRaft (vs Zookeeper)
Kafka 3.x introduziu o KRaft mode — o Kafka gerencia seus metadados internamente, sem depender do Apache ZooKeeper. Mais simples de operar e mais performático.

📬 Garantias de Entrega (Delivery Semantics)

O Kafka suporta três modos de entrega, e a escolha impacta diretamente performance vs segurança:

At-most-once — a mensagem pode ser perdida, mas nunca é processada duas vezes. Usado em métricas de baixo valor onde perda é aceitável.

At-least-once — a mensagem nunca é perdida, mas pode ser processada mais de uma vez em caso de falha. O consumer precisa ser idempotente para lidar com duplicatas. É o padrão mais comum.

Exactly-once — a mensagem é processada exatamente uma vez, sem perdas e sem duplicatas. Usa transações Kafka. Mais caro computacionalmente, mas necessário para sistemas financeiros.

Aspecto Apache Kafka Fila Tradicional (RabbitMQ) Banco de Dados
Modelo Log distribuído e persistente Fila com delete após consumo Tabelas com estado atual
Retenção Configurável (dias/GB) Mensagem deletada ao consumir Enquanto não deletar
Replay Sim — consumers relebem histórico Não Só se tiver audit log
Throughput Milhões de msgs/seg Dezenas de milhares/seg Depende do hardware
Caso de uso Streaming, event sourcing, ETL Tarefas assíncronas simples Estado atual de entidades

Quiz de Verificação

+120 XP
1. Um sistema de IoT produz 50.000 leituras de sensores por segundo. Os dados precisam ser consumidos por três sistemas distintos: um de alertas em tempo real, um de armazenamento histórico e um de dashboard. Por que o Kafka é a escolha ideal nesse cenário?
A Kafka armazena os dados em formato colunar, otimizando consultas OLAP nos três sistemas
B Os três sistemas podem consumir o mesmo tópico de forma independente, sem que um afete o outro, e o Kafka suporta o throughput necessário
C Kafka replica automaticamente os dados para MongoDB, Cassandra e o dashboard simultaneamente
D Kafka usa QUORUM consistency como o Cassandra para garantir que todos os sistemas recebam os dados
✅ Correto! +40 XP O Kafka usa o modelo publish-subscribe: múltiplos consumer groups podem ler o mesmo tópico de forma independente, cada um com seu próprio offset. O sistema de alertas, o de armazenamento e o dashboard são grupos separados — se um ficar para trás ou cair, os outros continuam operando normalmente.
❌ Pense no modelo pub-sub: o Kafka permite que múltiplos consumer groups independentes leiam o mesmo tópico, cada um mantendo seu próprio offset. Isso é o que desacopla os sistemas.
2. Um tópico Kafka tem 6 partições e você tem 4 consumers no mesmo consumer group. Como o Kafka distribui as partições?
A Erro — o número de consumers deve ser igual ao número de partições
B Cada consumer recebe 6 partições (broadcast)
C Dois consumers ficam com 2 partições cada, e dois ficam com 1 partição cada — e isso é válido
D As 6 partições vão para um único consumer líder; os demais ficam em standby
✅ Exato! +40 XP O Kafka distribui as partições entre os consumers disponíveis de forma balanceada — não é obrigatório ter um consumer por partição. A regra é: uma partição só vai para um consumer por vez dentro do mesmo grupo, mas um consumer pode ficar com várias partições. Se você tivesse 7 consumers, um ficaria ocioso.
❌ Lembre: o Kafka distribui as N partições entre M consumers. Se N > M, alguns consumers ficam com mais de uma partição. A regra é que cada partição vai para no máximo um consumer por grupo.
3. Qual é a diferença fundamental entre at-least-once e exactly-once delivery no Kafka, e qual das duas exige que o consumer seja idempotente?
A Exactly-once pode perder mensagens; at-least-once garante entrega. Exactly-once exige idempotência.
B At-least-once garante entrega mas pode duplicar; exactly-once garante entrega sem duplicatas. At-least-once exige consumidor idempotente.
C São equivalentes — a diferença é só de nomenclatura do Kafka
D At-most-once e at-least-once são sinônimos; exactly-once não existe no Kafka open source
✅ Perfeito! +40 XP No modo at-least-once, se o consumer processar uma mensagem mas falhar antes de confirmar o offset (commit), o Kafka reenviará a mensagem. Por isso o consumer precisa ser idempotente — processar a mesma mensagem duas vezes deve ter o mesmo efeito que processar uma vez. Exactly-once usa transações Kafka para garantir isso automaticamente, mas a um custo maior de latência.
❌ Em at-least-once: entrega garantida, mas possível duplicata → consumer precisa ser idempotente. Em exactly-once: sem perda e sem duplicata, mas usa transações Kafka (mais caro). At-most-once: pode perder mensagens, sem duplicata.

Criar o Producer Python
Este script simula 3 sensores IoT enviando leituras de temperatura a cada segundo.
PYTHON~/producer.py
import json
import time
import random
from datetime import datetime
from kafka import KafkaProducer

# Inicializar o producer
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

SENSORES = ['sensor-01', 'sensor-02', 'sensor-03']

print("🚀 Producer iniciado — enviando eventos para 'sensores-iot'...")

for i in range(30):  # 30 eventos
    evento = {
        "sensor_id": random.choice(SENSORES),
        "temperatura": round(random.uniform(18.0, 45.0), 2),
        "umidade": round(random.uniform(30.0, 90.0), 2),
        "timestamp": datetime.now().isoformat(),
        "seq": i + 1
    }
    producer.send('sensores-iot', value=evento)
    print(f"[{i+1:02d}] Enviado: {evento['sensor_id']} → {evento['temperatura']}°C")
    time.sleep(1)

producer.flush()
print("✅ Producer finalizado.")
producer.close()
4
Criar o Consumer Python com processamento
O consumer vai ler os eventos e emitir alertas quando a temperatura ultrapassar 40°C.
PYTHON~/consumer.py
import json
from kafka import KafkaConsumer

LIMITE_TEMP = 40.0

consumer = KafkaConsumer(
    'sensores-iot',
    bootstrap_servers='localhost:9092',
    auto_offset_reset='earliest',  # ler desde o início
    group_id='grupo-alertas',
    value_deserializer=lambda m: json.loads(m.decode('utf-8'))
)

print("👂 Consumer aguardando eventos em 'sensores-iot'...")
print(f"⚠️  Alerta de temperatura acima de {LIMITE_TEMP}°C\n")

total_eventos = 0
alertas = 0

for msg in consumer:
    evento = msg.value
    total_eventos += 1

    # Processar evento
    status = "🔴 ALERTA" if evento['temperatura'] > LIMITE_TEMP else "✅ OK"
    if evento['temperatura'] > LIMITE_TEMP:
        alertas += 1

    print(
        f"[seq={evento['seq']:02d}] {status} | {evento['sensor_id']} | "
        f"{evento['temperatura']}°C | Offset: {msg.offset} | Partition: {msg.partition}"
    )

    # Após 30 eventos, exibir resumo e parar
    if total_eventos >= 30:
        print(f"\n📊 RESUMO: {total_eventos} eventos | {alertas} alertas ({alertas/total_eventos*100:.0f}%)")
        break

consumer.close()
