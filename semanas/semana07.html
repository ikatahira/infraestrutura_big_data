📋 REVISÃO · S06 — Introdução ao NoSQL e o Teorema CAP

Na semana passada você compreendeu por que os bancos relacionais não escalam para Big Data: o modelo ACID rígido, o schema fixo e a dificuldade de escala horizontal são gargalos reais. Você conheceu os 4 tipos de bancos NoSQL (Chave-Valor, Colunar, Documentos, Grafos) e o Teorema CAP, que diz que um sistema distribuído pode garantir no máximo dois de três atributos: Consistência, Disponibilidade e Tolerância a Partição. Hoje você vai colocar a mão na massa no mais popular banco de documentos do mundo — o MongoDB — que optou por CP no triângulo CAP e se especializa em dados semi-estruturados com schema flexível.

Arquitetura e Conceitos Fundamentais

🤔 O QUE É O MONGODB E POR QUE ELE EXISTE?

Em 2007, engenheiros da empresa DoubleClick (publicidade digital) perceberam que o MySQL não aguentava o ritmo: o schema rígido atrasava deploys, e escalar horizontalmente era doloroso. A solução foi criar um banco onde cada registro é um documento JSON independente, sem obrigação de ter os mesmos campos. O resultado foi o MongoDB — lançado em 2009 como open source. Hoje é o banco de documentos mais usado do mundo, presente em startups e grandes empresas. A filosofia central é: guardar dados como você pensa neles, não forçar tudo em tabelas planas.

🗄
Database
Container de alto nível. Um servidor MongoDB pode ter vários databases (ex: loja, analytics). Equivale ao schema/banco no SQL.
📁
Collection
Agrupa documentos relacionados. Diferente de uma tabela SQL, não exige schema fixo — cada doc pode ter campos diferentes. Equivale à tabela.
📄
Document
A unidade básica de dados. É um objeto BSON (Binary JSON) com pares chave-valor. Pode ter arrays e documentos aninhados. Equivale a uma linha.
🔑
_id
Campo obrigatório único em todo document. Por padrão é um ObjectId de 12 bytes gerado automaticamente. Pode ser customizado. Equivale ao PRIMARY KEY.
🔍
Index
Estrutura B-Tree que acelera consultas. Sem índice, o MongoDB faz COLLSCAN (varre tudo). Com índice, faz IXSCAN. Use createIndex().
🔗
Aggregation Pipeline
Sequência de estágios que transformam documentos: $match filtra, $group agrupa, $sort ordena, $project projeta campos.
📊
BSON
Binary JSON — formato interno do MongoDB. Suporta tipos extras: Date, ObjectId, Binary, Decimal128. Mais eficiente que JSON puro.
🔄
Replica Set
Conjunto de 3+ servidores: 1 Primary (escrita) e N Secondaries (leitura/failover). Em produção, nunca rode MongoDB sem replica set.

⚠️ EMBED vs REFERENCE — A DECISÃO MAIS IMPORTANTE DO MONGODB

Embeddar significa colocar um documento dentro do outro (ex: endereço dentro de cliente). É mais rápido para leitura — 1 query traz tudo. Use quando os dados sempre são lidos juntos e o sub-documento não cresce indefinidamente.

Referenciar é guardar o _id do outro documento (similar a FK no SQL). Use quando os dados são grandes, acessados independentemente, ou compartilhados entre vários documentos. A filosofia MongoDB é: design pela forma como você consulta, não pela forma como os dados existem.

Quiz de Verificação

+120 XP
Q1 Uma aplicação de e-commerce precisa armazenar produtos onde cada produto pode ter atributos completamente diferentes: eletrônicos têm voltagem e garantia, roupas têm tamanho e cor. Por que o MongoDB é mais adequado que o MySQL nesse caso?
✅ Correto! +40 XP
Explicação aprofundada: No MySQL, adicionar o campo voltagem para eletrônicos exigiria um ALTER TABLE que afetaria toda a tabela — incluindo produtos de roupas que nunca terão voltagem. Isso gera muitos NULLs e slows down em tabelas grandes. No MongoDB, você simplesmente insere o documento com os campos que precisar. Collections diferentes para cada tipo de produto também é uma opção válida.
❌ Pense no problema do schema: em SQL, todos os produtos compartilham as mesmas colunas. Se um tipo de produto tem atributos únicos, você fica com muitos campos NULL nos outros registros. O MongoDB resolve isso com schema flexível — cada documento define seus próprios campos.
Q2 Você tem uma collection pedidos e precisa encontrar todos os pedidos com status "pendente" e valor total maior que R$200. Qual query mongosh está correta?
✅ Exato! +40 XP
Por que as outras estão erradas? A opção A usa sintaxe SQL que não existe no mongosh. A opção B passa os dois critérios como argumento separados: o segundo objeto em find() é a projeção (quais campos retornar), não um filtro. A opção D é sintaxe inventada. A correta passa um único objeto com todos os filtros: múltiplos campos no mesmo objeto formam um AND implícito.
❌ Atenção à sintaxe do find(): ele recebe até 2 argumentos — o filtro e a projeção. Para combinar múltiplos critérios de filtro, todos devem estar no mesmo objeto. O $gt é um operador de comparação ("greater than"). Multiple fields in the same filter object = AND implícito.
Q3 Em um sistema de blog, posts têm comentários. Você deve guardar os comentários dentro do documento do post (embed) ou em uma collection separada de comentários (reference)?
✅ Perfeito! +40 XP
Regras práticas de embed vs reference:
✔ Embeddar quando: os dados são sempre consultados juntos, a relação é 1-para-poucos, o sub-documento não cresce indefinidamente (limite de 16MB por documento no MongoDB).
✔ Referenciar quando: os dados crescem ilimitadamente, são consultados independentemente, ou são compartilhados por vários documentos. Em blogs reais, comentários de posts virais podem ter milhares de entradas — reference é mais seguro.
❌ A decisão embed vs reference é a mais crítica no MongoDB e não tem uma regra absoluta. O MongoDB suporta sim relacionamentos com $lookup. A normalização é um conceito SQL — no MongoDB, o objetivo é otimizar para como você consulta, e às vezes denormalizar (embeddar) é a escolha certa.

Importar a chave GPG oficial do MongoDB
O apt precisa da chave criptográfica para verificar que o pacote é legítimo. Sem ela, a instalação falha com erro de autenticação. O MongoDB mantém seu próprio repositório APT separado do Ubuntu.

# Instalar curl e gnupg (podem já estar instalados)
sudo apt-get install -y gnupg curl

# Importar a chave GPG do MongoDB 7.0
curl -fsSL https://www.mongodb.org/static/pgp/server-7.0.asc | \
  sudo gpg -o /usr/share/keyrings/mongodb-server-7.0.gpg \
  --dearmor

READ — Consultas com filtros, projeções e ordenação
As consultas no MongoDB são feitas com find(). O primeiro argumento é o filtro, o segundo é a projeção (quais campos mostrar). Operadores de comparação: $gt >, $lt <, $gte ≥, $lte ≤, $ne ≠, $in dentro de lista.
MONGOSHconsultas READ
# ─── READ ────────────────────────────────────────────

# Listar todos os documentos da collection
db.produtos.find()

# Filtrar apenas eletrônicos
db.produtos.find({ categoria: "eletronicos" })

# Filtrar por preço menor que R$1000
db.produtos.find({ preco: { $lt: 1000 } })

# Múltiplos filtros (AND implícito): eletrônicos com estoque acima de 10
db.produtos.find({
  categoria: "eletronicos",
  estoque: { $gt: 10 }
})

# Projeção: mostrar só nome e preço, ocultar _id
db.produtos.find(
  {},
  { nome: 1, preco: 1, _id: 0 }
)

# Ordenar por preço decrescente e limitar a 2 resultados
db.produtos.find().sort({ preco: -1 }).limit(2)

# Buscar exatamente 1 documento (retorna objeto, não array)
db.produtos.findOne({ nome: "Camiseta Polo" })

# Contar quantos produtos há por categoria
db.produtos.countDocuments({ categoria: "eletronicos" })

UPDATE e DELETE — Modificar e remover documentos
Operadores de update mais usados: $set define/atualiza campos, $inc incrementa/decrementa números, $unset remove campos, $push adiciona ao array, $pull remove do array.
MONGOSHUPDATE e DELETE
# ─── UPDATE ──────────────────────────────────────────

# $set: atualizar o preço e adicionar campo desconto
db.produtos.updateOne(
  { nome: "Notebook Dell XPS 13" },
  { $set: { preco: 4199.90, desconto: true } }
)

# $inc: decrementar estoque em 3 (simulando uma venda)
db.produtos.updateOne(
  { nome: "Mouse Logitech MX Master 3" },
  { $inc: { estoque: -3 } }
)

# $push: adicionar uma tag ao array de tags
db.produtos.updateOne(
  { nome: "Notebook Dell XPS 13" },
  { $push: { tags: "oferta" } }
)

# updateMany: aplicar desconto em todos os eletrônicos
db.produtos.updateMany(
  { categoria: "eletronicos" },
  { $set: { emPromocao: true } }
)

# ─── DELETE ──────────────────────────────────────────

# Remover um documento específico
db.produtos.deleteOne({ nome: "Camiseta Polo" })

# Verificar que foi removido

🪟 DIFERENÇAS DO WSL 2 EM RELAÇÃO AO UBUNTU NATIVO

O WSL 2 (Windows Subsystem for Linux) roda um kernel Linux real, mas não usa systemd por padrão em versões mais antigas. A instalação do MongoDB é idêntica, mas o gerenciamento do serviço é diferente. A partir do WSL 2 versão recente (Windows 11 com atualização 22H2+), o systemd pode ser habilitado. Abaixo mostramos os dois métodos.

1
Instalar MongoDB no WSL (mesmo processo do Ubuntu)
Abra o Windows Terminal e selecione a distribuição Ubuntu. Os comandos de instalação são idênticos ao Ubuntu nativo.
BASHWSL Terminal
# Importar GPG key
sudo apt-get install -y gnupg curl
curl -fsSL https://www.mongodb.org/static/pgp/server-7.0.asc | \
  sudo gpg -o /usr/share/keyrings/mongodb-server-7.0.gpg --dearmor

# Adicionar repositório
echo "deb [ arch=amd64,arm64 signed-by=/usr/share/keyrings/mongodb-server-7.0.gpg ] \
https://repo.mongodb.org/apt/ubuntu jammy/mongodb-org/7.0 multiverse" | \
  sudo tee /etc/apt/sources.list.d/mongodb-org-7.0.list

# Instalar
sudo apt-get update && sudo apt-get install -y mongodb-org
2
Verificar se systemd está disponível no WSL
WSL 2 recente suporta systemd. Veja o método adequado para sua versão:
BASHWSL — verificar systemd
# Verificar se systemd está ativo
ps -p 1 -o comm=
# Se retornar "systemd" → use Método A
# Se retornar "init" → use Método B
BASHMétodo A — com systemd (WSL moderno)
# Criar diretório de dados (necessário no WSL)
sudo mkdir -p /data/db
sudo chown -R mongodb:mongodb /data/db

# Iniciar via systemctl (igual ao Ubuntu)
sudo systemctl start mongod
sudo systemctl status mongod
BASHMétodo B — sem systemd (WSL legado)
# Criar diretório de dados
sudo mkdir -p /data/db
sudo chmod 777 /data/db

# Iniciar o mongod diretamente (em background)
mongod --dbpath /data/db &

# Verificar se está rodando
ps aux | grep mongod | grep -v grep

3
Conectar via mongosh e executar CRUD
A partir deste ponto, os comandos dentro do mongosh são idênticos ao Ubuntu nativo. Copie os passos 5, 6 e 7 da aba Ubuntu.

# A partir daqui: execute os mesmos comandos da aba Ubuntu

⚠️ WSL: Fechar o terminal encerra o mongod

No método B (sem systemd), quando você fecha o terminal WSL, o processo mongod é encerrado. Para manter rodando em sessões futuras, sempre execute mongod --dbpath /data/db & antes do mongosh. Para systemd no WSL, adicione o habilitador: sudo systemctl enable mongod.

2
Aggregation Pipeline — Relatório de vendas por vendedor
O pipeline processa documentos em etapas sequenciais. Cada estágio recebe a saída do anterior. Os estágios principais: $match filtra, $group agrupa/calcula, $sort ordena, $project formata a saída, $limit limita.
MONGOSHaggregation pipeline
// Pipeline: receita total e qtd de vendas por vendedor
db.vendas.aggregate([
  // Estágio 1 — $match: filtrar apenas 2024
  {
    $match: {
      data: { $gte: new Date("2024-01-01") }
    }
  },
  // Estágio 2 — $group: agrupar por vendedor
  {
    $group: {
      _id: "$vendedor",
      totalReceita: { $sum: { $multiply: ["$valor", "$quantidade"] } },
      totalVendas:  { $sum: "$quantidade" },
      numPedidos:   { $count: {} }
    }
  },
  // Estágio 3 — $sort: ordenar por receita decrescente
  { $sort: { totalReceita: -1 } },
  // Estágio 4 — $project: renomear e formatar campos
  {
    $project: {
      _id: 0,
      vendedor: "$_id",
      totalReceita: { $round: ["$totalReceita", 2] },
      totalVendas: 1,
      numPedidos: 1
    }
  }
])

Criar índices e analisar performance com explain()
Um índice acelera as consultas criando uma estrutura B-Tree nos campos indexados. Sem índice, o MongoDB faz COLLSCAN (varre todos os documentos). Com índice, faz IXSCAN. Use explain() para ver o plano de execução.
MONGOSHíndices e explain
// Ver índices existentes (só o _id por padrão)
db.vendas.getIndexes()

// Antes do índice: analisar plano de execução
db.vendas.find({ vendedor: "Ana" }).explain("executionStats")
// Procure: "stage": "COLLSCAN" → varre tudo!

// Criar índice simples no campo vendedor
db.vendas.createIndex({ vendedor: 1 })

// Após o índice: mesmo explain
db.vendas.find({ vendedor: "Ana" }).explain("executionStats")
// Agora: "stage": "IXSCAN" → usa o índice!

// Índice composto: útil para filtros combinados
db.vendas.createIndex({ categoria: 1, data: -1 })

// Listar índices criados
db.vendas.getIndexes()
▶ SAÍDA getIndexes() após criação
[ { v: 2, key: { _id: 1 }, name: '_id_' }, { v: 2, key: { vendedor: 1 }, name: 'vendedor_1' }, { v: 2, key: { categoria: 1, data: -1 }, name: 'categoria_1_data_-1' } ]

🔭 PRÓXIMA AULA · S08 — Apache Cassandra: Escala Sem Limites

Na Semana 08 você vai conhecer o Apache Cassandra — um banco colunar distribuído com arquitetura completamente diferente do MongoDB. Enquanto o MongoDB usa um modelo de documentos com schema flexível e tem um nó primário, o Cassandra é peer-to-peer: não existe master, qualquer nó aceita escritas, e ele foi projetado para nunca ficar indisponível. É a escolha do Netflix, Instagram e Discord para dados de alta escala.

Arquitetura peer-to-peer e consistent hashing — como o Cassandra distribui dados sem master CQL (Cassandra Query Language) — parecida com SQL, mas com limitações importantes O princípio Model by Query: você cria tabelas para cada consulta, não por entidade Consistência tunável: ONE, QUORUM, ALL — como calibrar disponibilidade vs consistência Missão prática: instalar Cassandra 4.x no Ubuntu e WSL, criar keyspace, modelar dados IoT
