🌐 Como as Máquinas se Encontram na Rede
Toda a infraestrutura de Big Data — do seu notebook a um cluster de 500 máquinas — depende de máquinas conversando entre si pela rede. Sem isso, não existe processamento distribuído.

Endereço IP — o "endereço de rua" de uma máquina na rede (ex: 192.168.1.10). Pode ser IPv4 (o mais comum) ou IPv6. Redes locais costumam usar faixas privadas como 192.168.x.x ou 10.x.x.x.

Porta — o "número do apartamento" dentro do IP. Uma máquina roda dezenas de serviços ao mesmo tempo (web, SSH, banco de dados), cada um numa porta diferente. Ex: HTTP usa a porta 80, SSH usa a 22.

Protocolo TCP/IP — o "idioma" combinado entre as máquinas para trocar dados sem perder nada no caminho, mesmo que a mensagem precise passar por várias redes intermediárias.

DNS — o "catálogo de nomes": traduz nomes fáceis de lembrar (google.com) para o IP real da máquina, porque decorar números seria inviável.

🖧 Cliente-Servidor e Topologia de um Cluster
Cliente-servidor — o modelo mais comum de comunicação: o cliente pede algo (ex: seu terminal rodando hdfs dfs -ls), o servidor responde (ex: o NameNode do Hadoop). A maioria dos serviços de Big Data segue esse padrão.

LAN (rede local) — a rede que conecta máquinas fisicamente próximas (mesmo prédio/datacenter). Um cluster Hadoop normalmente roda todo dentro da mesma LAN, para minimizar o tempo de resposta (latência) entre os nós.

Master/Worker — o padrão de arquitetura usado por praticamente toda ferramenta de Big Data (Hadoop, Spark, Kafka): 1 (ou poucos) nós master coordenam o trabalho, e vários nós worker executam as tarefas. É rede que permite essa coordenação acontecer.

Firewall e portas abertas — em um cluster real, é preciso liberar portas específicas entre os nós (ex: a porta 9870 do NameNode) para que a comunicação não seja bloqueada por segurança — uma das causas mais comuns de "cluster não funciona" no mundo real.

📄 Exemplo de gabarito (professor): saída esperada de cada comando desta missão, com anotações do que observar, está disponível em modelo_solucao_atividades_semana02.docx →
01
Descobrir o IP da sua VM
No terminal Ubuntu que você preparou na Semana 01:
bash
ip a # ou, em versões mais antigas: ifconfig
02
Testar conectividade com ping
O comando ping verifica se uma máquina consegue "conversar" com outra:
bash
ping -c 4 google.com ping -c 4 8.8.8.8
03
Ver quais portas estão abertas na sua máquina
Todo serviço rodando ocupa uma porta — vamos listar:
bash
sudo ss -tulnp # -t: TCP -u: UDP -l: escutando -n: numérico -p: mostrar processo
04
Resolver um nome de domínio manualmente
Veja o DNS traduzindo um nome em IP:
bash
nslookup google.com # ou: dig google.com
ℹ️ Conecte com a Semana 01: lembra do VirtualBox pedindo para configurar a "Rede" da VM (NAT, Bridge)? Isso definia como sua VM se conecta a essa mesma rede que você acabou de explorar.
05
Testar a comunicação entre dois serviços com curl
curl simula um cliente pedindo dados de um servidor — o mesmo modelo do Hadoop:
bash
curl -I https://www.google.com # -I mostra só os headers da resposta HTTP
